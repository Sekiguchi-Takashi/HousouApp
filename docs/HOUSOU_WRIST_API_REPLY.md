## 1. 草案への修正要求(2点)

### 1.1 【要修正】`/wrist/poll` の `since` だけでは端末を特定できない

草案 §5.1 は `GET /wrist/poll?since=<last_seq>` だが、`seq` は §9 で
「端末ごとに採番」とされている。ヘッダの `X-Housou-Device` で端末を
識別する前提と読めるが、**明記されていない**ため実装が割れる。

→ **ヘッダ `X-Housou-Device` を全エンドポイントで必須**とし、
`seq` の名前空間は `(device_id)` ごとに閉じることを本文に明記してほしい。
親機はこの前提で実装する。

### 1.2 【要修正】`/wrist/ack` `/wrist/answer` の冪等性

再送・二重送信は必ず起きる(電波が切れた瞬間のリトライなど)。

- `ack`: 同一 `seq` への複数回 ack は**2回目以降を無視**し、`{"ok":true}` を返す
  (エラーにしない)。初回の `acked_at` を保持する
- `answer`: 草案通り**最後の回答で上書き**。ただし `expires_at` 経過後の
  回答は `{"ok":false,"reason":"expired"}` を返す。時計側はこれを
  「送信失敗」ではなく「期限切れ」として表示してほしい(§8.2の
  `Send failed` とは別文言。ASCII `Expired` / 日本語 `期限切れ`)

## 2. 未決事項への回答

### Q1. ポート → **新規 45306 を切る。既存45304への相乗りはしない**

理由:

- 45304は災害放送の外部トリガー専用で、**PIN一致だけで全館放送が発報できる**
  極めて強い権限を持つ。ここに手首連携の日常的なトラフィックを混ぜると、
  認証方式を分ける必要が生じて設計が複雑になる
- 45304は `GET /fire?...` のクエリ形式、手首連携は JSON ボディの POST を含む。
  同一ポートで2つの流儀を混在させる利点がない
- 障害切り分け、ログ、将来の遮断(手首連携だけ止める)が独立してできる

**45306 を `PORT_WRIST` として確保する。** 既存45300-45305の役割は変更しない。

### Q2. 認証 → **既存QR登録の流用はしない。手首用の専用トークンを新設する**

既存のQR端末登録(`Qr.payload()`)は端末ID・IP・フロア等を平文で持つだけで、
**共有秘密(トークン)を払い出す仕組みが存在しない**。制御ポート45301は
LAN内無認証で動いている。ここに認証概念を後付けすると既存端末との
互換性を壊すため、手首連携は独立した認証を持つ。

**方式: 親機が発行する端末トークン(16桁英数)**

1. 管理者が親機の「手首端末」画面で登録を作成する
   → 装着者名と `device_id`(親機が採番、`w-` + 6桁)、`token`(16桁)を生成
2. 画面にQRを表示する。ペイロードは以下(既存QRとは別スキーム):
   ```
   housou://wrist?host=<親機IP>&port=45306&dev=w-a1b2c3&token=<16桁>
   ```
3. 装着者スマホの中継アプリ、または時計の設定画面でこれを読み取る/入力する
4. 以降、全リクエストに `X-Housou-Device` と `X-Housou-Token` を付ける

- トークンは親機の `SharedPreferences` に保持。管理者画面から無効化・再発行できる
- 認証失敗は `401` を返し、親機のログ(`security`)に記録する
- **平文HTTP**である点は既存の外部トリガーと同じ割り切り。LAN内/VPN内前提

**Pebble側への影響**: 草案§8.3の設定画面3項目(IP/ポート/トークン)に加えて
`device_id` の欄が必要になる。手入力が煩雑なら、装着者スマホの中継側で
QRを読んで時計へ配る形でもよい(そこはPebble側の裁量)。

### Q3. 自由入力時のASCIIラベル → **(a) 必須入力。ただし入力補助を付ける**

(b)のローマ字自動変換は、「昼食」→`Chushoku` のような**英語話者にも
日本語話者にも読めない文字列**を生む。7文字制限下では特に破綻する。
(c)の `(no label)` は、ascii表示の装着者にとって情報がゼロになる。

したがって **(a) を採用**するが、管理者の負担を下げるため以下を実装する:

- 自由入力欄に**よく使う語のASCII候補を辞書として同梱**し、
  日本語を入れると候補をサジェストする
  (例: 外食→`Eat out` / 家で→`At home` / 後で→`Later` / 未定→`Not yet` /
  はい→`Yes` / いいえ→`No` / 待って→`Wait` / 行く→`Go` / 行かない→`Skip`)
- 辞書に無い場合のみ管理者が英字を入力する。**空欄では送信させない**
- ASCII欄にも文字数カウンタを出す(質問20 / 選択肢14)

### Q4. 表示モードの管理 → **装着者が時計側で選ぶ方式を採用(草案通り)**

親機側で管理する方式は採らない。理由:

- 言語パックは装着者が任意に入れたり消したりできるものであり、
  **親機の登録情報は容易に実態とずれる**。ずれたときに文字化けするのは装着者
- 管理者が装着者の時計の状態を継続的に把握する運用コストが見合わない

ただし `/wrist/poll` のレスポンスに**参考情報として**
`"display_hint": "ascii"` を含めることは許容する(親機の管理画面で
装着者が自己申告した値。時計側は無視してよい)。
時計側の設定が常に優先されるという原則は崩さない。

### Q5. 回答の可視化 → **管理者画面 + ログ + CSV に載せる。日報とSLAには載せない**

- **管理者画面**: 手首端末ごとの最新メッセージ/質問と、既読・回答の状態を一覧表示
- **ログ**: 既存の `store.log()` に `kind="wrist"` を追加。送信・既読・回答を記録
- **CSV**: 既存のログ書き出しにそのまま含まれる(種別「手首」として出る)
- **日報**: 載せない。日報は「放送実績と設備の健全性」の文書であり、
  昼食の希望調査を混ぜると文書の目的がぼやける
- **月次SLA**: 載せない。SLAは放送設備の稼働率であり、手首の応答率は別の指標

将来、手首の応答率を見たい要求が出たら独立した集計として追加する。

### Q6. 対象者の粒度 → **端末単位を基本とし、グループ送信も可能にする**

既存の対象選択(全館/フロア/グループ/建物)をそのまま流用はしない。
理由は、手首端末は**設置物ではなく人が着けるもの**で、フロアや建物と
結びつかないため。「3階の手首端末」という概念は意味をなさない。

**採用する粒度:**

| 送信先 | 用途 |
|---|---|
| 個別 | 特定の1人に「電話して」 |
| 手首グループ | 「厨房班」「フロア係」など、手首端末だけで作る任意グループ |
| 全手首端末 | 全員への一斉アンケート |
| 子機スマホ(個別) | 手首を持たない相手への同内容の送信 |

手首グループは既存の端末グループとは**別の名前空間**として管理する。

## 5. 放送室側からの追加要望(Pebble側で検討してほしいこと)

いずれも**必須ではない**。実装コストが見合う範囲で判断してほしい。

1. **ポーリング失敗の可視化** — 親機に到達できない状態が続いたとき、
   時計の画面に小さく「圏外」相当の表示が出ると、装着者が
   「メッセージが来ない」のか「繋がっていない」のかを区別できる
2. **`server_time` の活用** — 時計とスマホの時刻ずれで `expires_at` の
   判定がずれる可能性がある。`server_time` との差分でオフセットを
   取ると堅い(親機側は常に `server_time` を返す)
3. **最後の1件の再表示** — 誤って閉じたメッセージをもう一度見たい、は
   必ず出る要求。直近1件だけ時計側に保持して再表示できると実用的

# 追補 v0.3.1 — 管理者スマホ単独構成（セルフ運用）

放送室 v1.8.1 で追加。**Pebble側の実装への影響は「接続先に 127.0.0.1 を
入力できるようにする」ことのみ**で、プロトコルの変更は一切ない。

## 経緯

v0.3 までの構成は [管理者スマホ] [装着者スマホ] [Pebble] の3者を前提としていた。
しかしこれだと、**管理者が自分の手首でも受け取りたい場合や、
管理者しかいない小規模運用で、2台目のスマホが必須**になってしまう。

## 追加した構成

```
[管理者スマホ] ─── Bluetooth ───> [Pebble]
  放送室アプリ(サーバ)
  ＋中継(PebbleKit JS)
   ↑ HTTP 127.0.0.1:45306 (同一端末内)
```

管理者スマホが**サーバと中継を兼ねる**。HTTPリクエストは同じ端末の
ループバックへ向かうため、外へは一切出ない。

## Pebble側で必要な対応

1. 設定画面のホスト欄に `127.0.0.1` を入力できること
   （IPアドレスの妥当性チェックでループバックを弾かないこと）
2. それ以外は既存実装のまま。エンドポイント・ヘッダ・JSON形式は同一

## 放送室アプリ側の実装（済）

- 手首タブに「⌚ この端末で使う（自分のPebble）」を追加
- 登録すると `self: true` の端末として扱い、接続情報に 127.0.0.1 を提示する
- セルフ端末は1台まで。一覧とは別枠に表示し、接続状態が分かるようにした
- 送信先の「全員」にはセルフ端末も含まれる（自分の手首にも届く）

## この構成の利点

- **2台目のスマホが不要**。管理者1人＋Pebble 1台で完結する
- **接続先が固定**。Wi-Fiが切れてもIPが変わっても設定を直す必要がない
  （通常構成では親機のIPが変わると全装着者が設定し直しになる）
- 通常構成と混在できる。管理者は自分の手首を 127.0.0.1 で使いつつ、
  他のスタッフにはQRを配る、という運用が可能

## 制約

- 管理者スマホでPebbleアプリと放送室アプリの両方が動いている必要がある
- Pebbleは1台のスマホとしかBluetooth接続できないため、
  管理者のPebbleは管理者スマホに紐づく（当然だが明記しておく）

# 追補 v0.6 — 変更依頼への回答（CHANGE_REQ v0.6案）

`HOUSOU_WRIST_CHANGE_REQ.md` への回答。放送室 v1.9 で実装済み。

## 結論: **依頼0・A・B・C をすべて承認、実装完了**

単一保留・明示的取り消し・日付基準の失効という方針は、
「気づかないうちに消えていた」を排除する点で運用上正しい。
親機側も同じ基準に揃えた。

## 依頼0-a: `cancel` 項目 → **承認・実装済み**

- `/wrist/poll` の items に `{"type":"cancel","target_seq":N,"seq":M}` を流す
- `target_seq` は常に明示して送る（省略はしない）
- cancel 項目は**日付をまたいでも配信する**。取り消しだけは確実に届ける必要があるため
- cancel 自体は `label_ja`/`label_ascii` を持たないため、`enqueue()` の検証を経由せず直接キューへ積む

管理者操作: 端末一覧の「✖ 取り消して解除」。確認ダイアログに
「最大◯秒後に届きます」とポーリング間隔を明示している。

## 依頼0-a2: 日付変更での失効 → **承認・親機も同基準に統一**

- 親機は**前日以前に投入された項目を配信しない**（`Wrist.poll()` で `dayOf()` 比較）
- 応答待ち判定も当日分のみ対象。日をまたいだ項目は自動的に応答待ちから外れる
- 手首から `reason: "day_change"` を受けたら「日をまたいで失効（未応答）」として記録

これで**手首と親機の失効基準が一致**し、ご指摘の食い違いは起きない。

## 依頼0-b: `expires_at` → **送信を廃止**

推奨案を採用し、`expires_at` フィールドを**一切送らなくした**。
`buildMessage()` / `buildQuestion()` から削除済み。

さらに `/wrist/answer` から**期限判定を撤去**した。
配信済みの項目は必ず受け取る。`expired` を返す経路は無くなった
（`{"ok":false,"reason":"not_found"}` は該当qidが存在しない場合のみ）。

## 依頼0-c: 未応答項目の可視化 → **承認・実装済み**

端末一覧に応答待ちを常時表示する。

```
🟢 田中                      接続中
厨房班 / w-a1b2c3
⏳ 応答待ち: 「昼食どうする?」#1042
この端末へは新しく送れません。取り消すと送れるようになります。
[ ✖ 取り消して解除 ]
```

## 依頼A: `POST /wrist/reject` → **承認・実装済み**

3種の reason をすべて受け付け、管理者画面と履歴に反映する。

| reason | 表示 |
|---|---|
| `busy` | 未達（応答待ちのため） |
| `dismissed` | 未応答のまま閉じられた |
| `day_change` | 日をまたいで失効（未応答） |

`dismissed` の扱いは**「NG」として記録**する（参考情報に留めない）。
装着者が見て閉じた事実は、既読とも未読とも異なる第3の状態であり、
管理者が再送を判断する材料になるため。

reject を受けた項目は応答待ちから外れ、その端末へ再び送信できる。

## 依頼B: 接続状態の表示 → **承認・実装済み**

`/wrist/poll` の受信時刻から**60秒以内なら「接続中」**（🟢）。
それ以外は⚪と最終通信時刻を表示する。ご提案の基準をそのまま採用した。

## 依頼C: 送信の抑止 → **承認・依頼Aと併用**

事前抑止と事後NGの両方を実装した。理由は、複数端末への一斉送信では
**送信時点で応答待ちの端末だけを自動的に除外**できると管理者の手間が減り、
かつ送信直後に相手が応答待ちになる競合は事前チェックでは防げないため、
事後の `busy` も引き続き必要になる。

具体的な挙動:

- 応答待ちの端末は**送信先から自動的に外す**
- 接続中でない端末は**送信するが警告に列挙**する（次回起動時に届くため）
- 全端末が応答待ちなら送信自体を中止し、取り消しを促す

```
確認
応答待ちのため送信しない端末:
・田中
接続中でない端末（届くのは次に時計アプリを開いたとき）:
・佐藤
2台へ「電話して」を送信します。
[やめる] [送信]
```

## 親機側の状態モデル（参考）

各項目は以下のいずれかの状態を持つ。

| 状態 | 条件 |
|---|---|
| 未配信 | まだ poll で返していない |
| 応答待ち | 配信済み、ack/answer/reject いずれも未受信、当日分 |
| 既読 | ack を受信 |
| 回答済み | answer を受信 |
| 未達/未応答 | reject を受信（busy / dismissed / day_change） |
| 取り消し済み | 管理者が cancel を発行 |

**応答待ちは端末あたり最大1件**という前提で `pendingSeq()` は
最も古い1件を返す。手首側の単一保留と整合する。
