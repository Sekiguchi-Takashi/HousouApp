## 1. 変更後の運用フロー(確定済み・Pebble側)

1. 普段は**別のウォッチフェイス**を表示している(HousouWatchは常駐しない)
2. 使うときに Pebble公式アプリの設定で**「受信を有効にする」をONにし**、
   時計でHousouWatchを起動する
3. 管理者は**手首端末が「接続中」であることを確認してから**メッセージを送る
4. 装着者は受け取ったメッセージ/質問に応答する。
   誤操作防止のため、応答せずに閉じるにはBACKを2回押す必要がある
5. **手首は同時に1件しか扱わない。** 1件が未応答のうちに届いた2件目は
   受け取らず、親機へNGを返す

## 1.5 依頼0(必須・v0.5で追加) — 取り消しと、期限による自然消滅の廃止

### 背景

当初は `expires_at` による自動消滅と、Pebble側の10分ウォッチドッグで
保留を解除していた。しかし**「気づかないうちに消えていた」状態は
運用上の判断が難しい**(装着者が見ていないのか、消えたのか、
届いていないのかを管理者が区別できない)。

そこで**時間経過で勝手に消える経路をすべて廃止**し、
代わりに管理者が明示的に取り消せるようにする。

### 依頼0-a: `cancel` 項目の新設

`/wrist/poll` の `items` に、取り消しを表す項目を流せるようにしてほしい。

```json
{
  "seq": 1045,
  "type": "cancel",
  "target_seq": 1042
}
```

- `target_seq`: 取り消したい項目の `seq`。**省略時は現在保留中の項目**を取り消す
- Pebble側は `type: "cancel"` を**保留の有無にかかわらず必ず処理**し、
  他の項目のように `busy` でNGを返すことはしない
- 対象が既に応答済み/未保留なら黙って無視する(エラーにしない)
- 取り消し後は保留が解けるため、管理者はすぐ別のメッセージを送れる

これにより「指示を取り消して別のメッセージに差し替える」が成立する。

### 依頼0-a2: 失効は日付変更まで(v0.6で追加)

「未応答の項目が永久に残る」のも運用しづらいため、
**唯一の時間による失効を「日付が変わるまで」に定めた。**

- Pebble側は保留中の項目を localStorage に保持し、
  **ローカル日付が変わった時点で失効**させる(親機時刻のオフセットを反映)
- 失効時は親機へ `POST /wrist/reject` を `reason: "day_change"` で送る
- 表示中なら時計の画面を閉じ「日付が変わり失効」と表示する
- 経過時間(何分・何時間)による失効は一切行わない

親機側でも同じ基準を採ることを推奨する。日をまたいだ未応答の項目は
翌日の管理者画面に「未応答のまま失効」として残し、配信対象からは外す。
**基準を日付に揃えておかないと、手首は失効したのに親機は応答待ちのまま、
という食い違いが起きる。**

### 依頼0-b: `expires_at` の扱い

Pebble側は **`expires_at` を見なくなった**(期限切れでも表示し、破棄しない)。
親機側も以下のいずれかにしてほしい。

- (推奨) `expires_at` を送らない、または十分長い値にする
- 期限切れ項目を配信しない既存の挙動は残してよい
  (配信されなければ手首には出ないため矛盾しない)

**避けたいのは「配信済みの項目が親機側の期限判定で無効になり、
装着者が応答したのに `expired` が返る」状態。**
その場合は取り消し(`cancel`)として明示的に流してほしい。

### 依頼0-c: 未応答項目の可視化

自然消滅がなくなるため、**未応答の項目は装着者が応答するか
管理者が取り消すまで残り続ける**。管理者画面に
「この端末は seq=1042 を応答待ち」と出し、
そこから直接「取り消して別のメッセージを送る」に進めると運用が回る。

## 2. 依頼A(必須) — `POST /wrist/reject` の新設

上記5のNG返却先が契約に存在しないため、新設をお願いしたい。

リクエスト:

```json
{
  "seq": 1044,
  "qid": "q-9a12",
  "reason": "busy",
  "rejected_at": "2026-08-16T12:35:10+09:00"
}
```

- ヘッダは他エンドポイントと同一(`X-Housou-Device` / `X-Housou-Token`)
- `qid` はメッセージの場合は空文字
- レスポンスは `{"ok":true}` を想定。**親機側で何もしなくても構わない**が、
  管理者画面に「未達(理由)」として出ると運用価値が高い

`reason` の値は3種類:

| reason | 意味 | 管理者への提示案 |
|---|---|---|
| `busy` | 先行する1件が未応答のため受け取らなかった | 「手首が応答待ちのため未達。応答後に再送してください」 |
| `dismissed` | 表示されたが応答されずに閉じられた | 「未応答のまま閉じられました」 |
| `day_change` | 日付が変わり失効した(未応答) | 「日をまたいだため失効。未応答」 |

### 補足: `seq` の扱い

Pebble側は reject した項目についても `since` を進める(同じ項目を
繰り返し受け取らないため)。したがって**NGになった項目は親機側から
再送しない限り二度と手首へ届かない**。管理者が再送する運用を前提とする。

## 3. 依頼B(任意) — 手首端末のオンライン状態を管理者画面に出す

上記フロー3のために、管理者が送信前に手首の状態を確認できると良い。

親機は `/wrist/poll` を受けた時刻を端末ごとに記録しているはずなので、
**最終ポーリング時刻から60秒以内なら「接続中」**と判定して
管理者画面に表示してほしい。Pebble側の追加実装は不要。

- 60秒: 既定のポーリング間隔20秒の3回分
- 「接続中」でない端末を送信先に選んだときは警告を出す、
  あるいは送信先候補から外す、といった扱いは放送室チャットの裁量

## 4. 依頼C(任意) — 送信の抑止

依頼Aが実装されるなら、そもそも**未応答の項目がある端末には
新規送信させない**方が管理者にとって分かりやすい可能性がある。

- 親機は端末ごとに「未応答の項目があるか」を把握できる
  (配信済みかつ ack/answer/reject のいずれも受けていない項目の有無)
- その状態の端末を送信先に選んだ場合、送信前に警告する

依頼Aで事後にNGを返す方式と、依頼Cで事前に止める方式は併用できる。
どちらを主にするかは放送室チャットで判断してほしい。

## 5. Pebble側の実装(HousouWatch v1.4、実装済み)

| 項目 | 内容 |
|---|---|
| 有効/無効スイッチ | 設定画面に追加。**既定はOFF**。OFFの間はポーリングしない |
| メイン画面 | 時刻・日付・接続状態(接続中/圏外/認証エラー/未設定/停止中) |
| 単一保留 | 1件を扱っている間は新着を受け取らず `/wrist/reject` へ `busy` |
| 保留の解除 | ack / answer の送信完了時。応答なしで閉じた場合は `dismissed` を送って解除 |
| 失効は日付変更のみ | 経過時間による消滅は全廃。日付が変わった時のみ失効させる |
| 保留の永続化 | localStorageに保持。アプリを開き直しても保留は維持される |
| 取り消し | `type: "cancel"` を受けたら表示中の項目を閉じ「取り消されました」を表示 |
| 誤操作防止 | メッセージ・質問画面ともBACK2回押しで閉じる(1回目は警告と振動) |
| 終了操作 | メイン画面のBACK短押しは無効。長押し(0.7秒)で終了 |

## 6. 未確定事項

  404で失敗するだけで、単一保留の制御自体は変わらず動作する。
  ただし**管理者は2件目が届いていないことを知る手段がなくなる**
- `dismissed` を「NG」として扱うか「参考情報」として扱うかは
  放送室チャットの判断に委ねる
- 依頼0-aが未実装の間、**管理者が取り消す手段が存在しない**。
  装着者が応答するまで、その端末へは新規送信ができない
  (2件目は `busy` でNGになる)。優先度は高い
